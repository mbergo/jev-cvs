Summary of the discussion

How the conversation led to these rules: from whether a Jev-like model can secure MCP, through how far it can go, to what CVS Health specifically needs.

Correction made along the way. "JEV" was first read as JEPA (joint-embedding predictive architecture), and the early answers were reasoned on that basis. The Studio page later showed that Jev is TypeSafe Jev, a non-autoregressive "System One" decision model. The JEPA-specific points in cards 1 and 2 (latent prediction, the cited papers) may therefore not describe Jev.

1Is there a known application to MCP security?

  • No published work was found applying a JEPA-style model to MCP security.
  • Closest work: SafeMCP (a world model on the MCP server that filters risky tools by look-ahead), MCPShield (a graph-based detector on tool-call traffic) and a latent-space measure of conversation drift.
  • Only search summaries were read, not the papers.

2The two most valuable uses

  • Anomaly detection on tool-call sequences: flag calls that do not fit the session so far. It catches the effect of injection and tool poisoning, trains on benign traffic only, and is cheap enough to run on every call.
  • Look-ahead before a call executes: predict where an action leads and block it if unsafe. Other models can do this, but at the cost of an LLM call per step.
  • This ranking is a judgment, not a tested result.

3Can it be a complete MCP security set?

No. It covers the behavioural layer; these stay deterministic and need code and policy:

  • Authentication, authorization and access control.
  • Transport, session and network isolation.
  • Supply chain: malicious server packages and dependencies.
  • Secrets handling and least privilege.
  • Anything that must never happen, which needs a hard rule or human approval.

4Design ideas discussed

  • About five varied examples per rule: enough to steer a pretrained model as prototypes, name the alert and set thresholds; not enough to train one. Vary the surface, keep the violation the same.
  • Benign near-misses per rule: they cut false positives more than extra attack examples do.
  • Reranker after encoding: improves precision on the flagged minority. Recall is capped by the first stage, and a reranker reading raw tool text can itself be injected.

5What remains weak, and what is strong

  • Still weak on the learned side: adaptive attackers, novel attacks that miss the first stage, drift in legitimate usage, and the need for a large clean benign corpus.
  • These apply to every detection-based measure, not only this one.
  • Strong: once the model exists, a new guardrail is a question plus a few examples, with no retraining.

6Review of the Studio and the CVS Health fit

  • The Studio has 30 rules: 6 PII, 1 credentials, 11 injection and execution, 3 harmful content, 9 confidential data.
  • Gaps for CVS Health: healthcare identifiers, stricter health-data categories and healthcare-specific misconduct. The 14 rules below fill them.
  • Possible bug: the policy builder applies rule modes only for the pii and prompt_injection categories, so confidential-data rules may stay at "allow". Only one source file was read.
  • Exposure: the site runs as a public Vite dev server, so its full source can be downloaded.
  • All rules judge request.prompt only; tool arguments and tool results are not yet covered.

Main sources: SafeMCP · MCPShield · Conversation drift in MCP · Caremark FTC settlement · Omnicare judgment · Aetna settlement · CVS–Criteo settlement · Health100

Setup

  1. Add the new group to GROUP_CATEGORY in src/data/controlPlaneRules.ts (first lines of the snippet).
  2. Append the rule({...}) entries to INITIAL_CONTROL_PLANE_RULES.
  3. Add each "benign near-miss" from the tables above to NEGATIVE_PRESET_PROMPTS so false positives are tested.
  4. "Healthcare Conduct" is mapped to the existing prompt_injection category, as "Harmful Content" already is. A dedicated category would need a change to the policy schema.
